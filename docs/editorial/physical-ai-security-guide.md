# フィジカルAIセキュリティのまとめ記事：実装メモと残タスク

対象ページ：`/guides/physical-ai-security`（実装は `src/pages/guides/[slug].astro`、
データは `src/services/editorial/guides.ts`）

## 仕組み

- 見出しと本文、見出しごとの関連記事スラッグを `guides.ts` に持っています。
  記事タイトル・日付は WordPress から実行時に取得するので、WP側でタイトルを直しても追従します。
- WordPress に存在しないスラッグは描画時に黙って除外されます（リンク切れを作らない）。
- 「最新動向」は `freshness.domain`（ロボット、工場など）と `freshness.aspect`
  （セキュリティ、安全など）の**両方**をタイトルに含む新しい記事を自動で拾うため、
  月次の手作業更新は不要です。条件を満たす記事がないあいだ、この節は表示されません。
- 記事側（`/articles/[slug]`）には、そのスラッグを参照しているガイドへの逆リンクが
  自動で出ます。**WordPress の本文を20本編集する必要はありません。**
- ガイドに記事を足すのは `guides.ts` の該当セクションに1行追加するだけです。

### 重複記事の統合（2026-11-03 実施）

3組を検討し、2組を統合、1組は残しました。統合した側は WordPress で下書きに戻し、
旧スラッグからの恒久リダイレクトを `vercel.json` に置いています。

`vercel.json` の `"permanent": true` が返すのは 301 ではなく **308**（RFC 7538 Permanent
Redirect）です。Google は 301 と同じ恒久リダイレクトとして扱うため、評価の引き継ぎに差は
ありません。文字どおり 301 を返したい場合は `"permanent": true` の代わりに
`"statusCode": 301` を指定します。2026-11-03 の統合作業のコミットメッセージと PR では
「301」と書いていますが、実際に返るのは 308 です。

#### 1本目（ARTEX）の書き方

タイトル案：「ARTEXとは？AIが自律的に侵入する時代に、中小企業がまず確認すべき7項目」

ITmediaなどの報道と同じ「何が起きたか」のニュース解説では勝てません。**守る側の実務ガイド**に
寄せて差別化します。GA4のデータでも、実務ガイド型がニュース解説型より読まれています。

構成：

1. チェックリスト（記事の主役）。JPCERTの注意喚起にある対策を、そのまま使える形にする。
   APIのレート制限、外部に出ている管理画面の閉鎖、権限の最小化などが含まれるはずだが、
   **項目は執筆時にJPCERTの注意喚起を読んで確定すること**（ここに書いた3つは例示であって、
   7項目の中身を確認したものではない）。
2. 時系列。GitHubでの公開 → 悪用の報告 → 作者による公開停止 → 改変版の拡散 →
   JPCERTの注意喚起、という流れ。続報が出る前提で、更新していくセクションとして作る。
3. フィジカルAIとの接続。「AIで自律的に攻撃するツールが、工場やロボットのネットワークに
   向いたらどうなるか」という論点で、まとめ記事 `/guides/physical-ai-security` につなぐ。

書くときの線引き（インシデント一覧の掲載基準と同じ考え方）：

- **漏洩を公表した特定の企業を「ARTEXの被害企業」と結びつけない。** その企業自身がAIの関与を
  公表していないため。
- **ツールの使い方や攻撃手順の詳細には踏み込まない。** 仕組みの概要と防御策に絞る。
  読者層に合っているうえ、悪用の手引きにもならない。
- **出典は、JPCERT（行政）、GMOとAhnLab（調査会社）、報道を区別して書く。**
  どの事実が誰の発表によるものかが読者に分かる形にする。
